## Executive Summary / Загальний підсумок

Цей звіт аналізує результати останніх запусків навчання та оцінки дрейфу моделі `EOPKGTopologyConditioned` після впровадження справжнього розв'язання кандидатів (`candidate_identity_mode: topology_native` у коміті `c41cbd2`). 

Аналіз показує, що:
1. Параметр `training.topology_conditioning_wrong_version_negative_enabled: True` **ігнорується** (пропускається) у режимі `candidate_id`, що пояснює відсутність будь-якого впливу на метрики.
2. Зміна оцінки дрейфу та метрик (деградація F1 з ~0.69 до ~0.56 у drift-вікнах) є **артефактом виправлення оцінки**, а не реальним погіршенням якості моделі. У попередніх комітах технічні шлюзи (gateways з `class_index = -1`) фізично відкидалися з простору кандидатів під час тестування, що полегшувало завдання моделі. Тепер модель змушена працювати з повною топологією (включно зі шлюзами та unseen-вузлами), де вона накопичує до ~41% ймовірнісної маси на технічних вузлах.
3. Збільшення ваги регуляризації топологічного потоку (`topology_flow_penalty_weight` з `0.03` до `0.40`) дає чіткий позитивний ефект: знижує накопичення помилкової маси з `0.49` до `0.41` та підвищує `strict_val_macro_f1` з `0.40` до `0.635` у навчанні, але цього недостатньо для повного придушення технічних вузлів.

## Wrong Version Negative Loss / Вплив wrong_version_negative

Користувач звернув увагу, що вмикання негативного семплювання іншої версії топології (`topology_conditioning_wrong_version_negative_enabled: True`) не вплинуло на обчислення.

**Причина:**
У коді `ModelTrainer` (`src/application/use_cases/trainer.py`, ряди 2234-2254) обчислення втрати для негативів іншої версії процесу явно **пропускається** у режимі `candidate_id`:

```python
if (
    self.learning_strategy_config.wrong_version_negative_enabled
    and float(self.learning_strategy_config.wrong_version_negative_weight) > 0.0
):
    current_version = self._current_batch_version(contract)
    ...
    elif candidate_output is not None:  # Активно при candidate_contract_mode = candidate_id
        forward_stats["topology_conditioned_wrong_version_skipped_candidate_id_batches"] = int(
            forward_stats.get(
                "topology_conditioned_wrong_version_skipped_candidate_id_batches",
                0,
            )
        ) + 1
```

**Чому це зроблено:**
У режимі `candidate_id` простір кандидатів (`[B, C_v]`), allowed-маски та відповідності є динамічними й жорстко прив'язаними до конкретної версії процесу в батчі. Якщо просто замінити структурний payload (`wrong_payload`) на іншу версію процесу без перерахунку індексів кандидатів, це призведе до критичного збою вирівнювання тензорів та помилок розмірностей. Тому розрахунок цієї втрати було заблоковано для безпеки, а в MLflow збільшується лічильник пропущених батчів.

### Чому в попередній версії (`7925e81c` / `a5c84b64`) метрики були вищими?
До впровадження змін у коміті `c41cbd2`, метод `_pool_node_scores_to_dynamic_candidates` містив жорстку фільтрацію:
```python
valid = (node_to_class >= 0) & (node_to_class < self.output_dim)
candidate_class_index = torch.unique(node_to_class[valid], sorted=True)
```
Це означало, що всі технічні вузли шлюзів (`class_idx = -1`) та unseen-вузли **фізично видалялися з простору кандидатів** під час навчання та валідації. Модель обирала та розподіляла ймовірності лише серед відомих активностей. Саме тому:
1. `candidate_invalid_probability_mass` становила лише `0.04 - 0.08` (бо технічних вузлів у батчі просто не було).
2. Точність та F1 були штучно завищеними, оскільки модель ніколи не могла помилитися й передбачити технічний шлюз (що трактується як помилка/OOS при зворотній проекції на глобальні класи).

### Що змінилося в новій версії (`3277fdad` / `946857a7`)?
Після розв'язання ідентичності кандидатів (`topology_native`), простір кандидатів тепер формується безпосередньо з топології BPMN (наприклад, 41 кандидат для кредитного процесу, де 4 вузли є технічними шлюзами з `class_index = -1`).

Оскільки шлюзи ніколи не є цільовими таргетами в логах (XES містить лише бізнес-активності), модель під час навчання отримує для них нульовий таргет. Проте без сильного примусу вона продовжує виділяти на них значну ймовірнісну масу.
При значенні `topology_flow_penalty_weight: 0.03`, модель зливала **~49%** маси на ці технічні вузли. При збільшенні ваги штрафу до **0.40**, зливання зменшилося до **41.6%**, що дозволило моделі підняти валідний F1 на навчанні до **0.635** та на тесті до **0.759**.

Однак під час оцінки дрейфу (`3277fdad`) на нових версіях процесів модель знову прогнозує технічні вузли у ~17.7% випадків (метрика `drift_window_test_oos = 0.177`). Оскільки ці прогнози проектуються назад як `-1`, strict F1 падає до `0.566`.

## Key Conclusions & Next Steps / Висновки та перспективи

Методологія dynamic candidate scoring в межах локальної топології є теоретично правильною (вона дозволяє zero-shot роботу на нових версіях процесу без перебудови голови класифікатора), проте поточна реалізація має фундаментальні слабкості у придушенні технічних та неактивних топологічних шляхів.

### Чому навчання не працює ідеально?
1. **Проблема спільних ембедінгів шлюзів:** Всі технічні вузли ініціалізуються статичним параметром `self.struct_non_target_emb` з додаванням невеликого хеш-шуму. GNN-енкодер має занадто мало диференційованих ознак, щоб надійно відрізнити один технічний шлюз від іншого або від неактивної бізнес-активності.
2. **М'яка природа втрат:** Штраф `invalid_probability_mass` мінімізує суму ймовірностей неактивних вузлів через Softmax, але оскільки Softmax розподіляється на 41 клас, градієнти стають дуже розмитими. Моделі простіше "розмазати" невизначеність по технічних класах, ніж повністю виставити їхні логіти в `-inf`.

### Перспективи та варіанти вирішення (Next Steps):
Для досягнення dissertation-grade якості на zero-shot дрейфі необхідно впровадити один із наступних підходів:

1. **Explicit Negative Target Supervision (Жорсткий Negative Loss):**
   Замість м'якої втрати ймовірності, додати до функції втрат явний бінарний штраф (наприклад, Binary Cross Entropy або Margin Loss) конкретно для логітів технічних вузлів. Кожен технічний вузол у батчі має примусово каратися градієнтом, який виштовхує його логіт до `-1e4`, незалежно від Softmax інших вузлів.
2. **Semantic Grounding (Семантичне заземлення):**
   Реалізувати відкладений P1 борг `topology_native_candidate_semantic_grounding`. Технічні шлюзи повинні мати чіткі структурні або семантичні текстові ембедінги (наприклад, "XOR Gateway", "Parallel Split"), які дозволят GNN чітко відокремлювати їх від бізнес-активностей на рівні представлень.
3. **Gateway Collapse (Схлопування шлюзів на етапі підготовки):**
   Якщо бізнес-вимоги дозволяють передбачати лише бізнес-активності, технічні вузли шлюзів мають бути фізично видалені з графа топології ще на етапі `ingest-topology` / `collapse_for_prediction` (через транзитивне замикання ребер), щоб модель взагалі не бачила їх у просторі кандидатів `C_v`.
